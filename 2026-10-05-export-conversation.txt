     Plano: API de Tempo (tarefa-parte1.md)

     Contexto

     O tarefa-parte1.md pede uma API Laravel com três rotas:
     - autocomplete de municípios, a partir do cidades.json;
     - registro do clima de uma cidade, via OpenWeatherMap;
     - histórico das consultas, com cache.

     O banco é SQLite, e a regra anti-duplicidade e os testes são obrigatórios.
     O usuário vai implementar manualmente, então o entregável é um único 
     arquivo implementacao.md na raiz do projeto. Ele traz o código de cada
     arquivo com uma breve descrição acima de cada um. Nenhum arquivo da
     aplicação será criado ou alterado por mim.

     Estado atual: Laravel 13, PHP 8.3, DB_CONNECTION=sqlite,
     CACHE_STORE=database (nos testes, array). Ainda não existe routes/api.php.
     O bootstrap/app.php já renderiza JSON para api/*. O cidades.json tem o
     formato
     {"estados":[{"sigla":"AC","nome":"Acre","cidades":["Acrelândia",...]}]}.

     Decisões confirmadas com o usuário

     - Duplicidade: a nova consulta é comparada com a última consulta da mesma 
       cidade. Se temperatura, sensação, umidade e descrição forem iguais, só o
       consultado_em é atualizado. Se algum valor mudar, um novo registro é
       criado.
     - Histórico: GET /api/clima/historico?cidade=X, com o filtro de cidade
       opcional e ordem do mais recente para o mais antigo. O cache tem TTL e é
       invalidado a cada criação ou atualização.
     - POST: POST /api/clima?cidade=Campinas, só com o nome da cidade e sem
       validar na tabela de municípios. A OpenWeather recebe q=Campinas,BR.

     Decisões de design (minhas)

     - O nome salvo é o que a OpenWeather devolve (name), para padronizar a
       grafia. Além dele, guardo cidade_slug (Str::slug), que serve para três
       coisas: achar a última consulta, filtrar o histórico e montar a chave de
       cache. Assim, "sao paulo" e "São Paulo" são tratados como a mesma cidade.
     - A tabela de municípios ganha a coluna nome_normalizado (minúsculo e sem
       acento). Sem ela, o LIKE do SQLite não acharia "São" ao buscar "sao".
     - O provider fica atrás de uma interface (WeatherProviderInterface),
       registrada no AppServiceProvider. Isso facilita o mock e uma eventual
       troca de API.
     - Cache: chaves clima:historico:todas e clima:historico:{slug}, com TTL de
       10 min. Depois de gravar, o Service faz forget nas duas.
     - Os erros usam exceções próprias com render() em JSON, no formato {"erro":
       "mensagem"}:
       - cidade não encontrada: 404;
       - chave da API inválida ou erro 5xx da OpenWeather: 502;
       - timeout ou falha de conexão: 503;
       - validação: 422, com a mensagem em português no FormRequest.
     - O POST responde 201 quando cria um registro e 200 quando só atualiza a
       data. O corpo inclui o campo atualizado: true|false.
     - A rota de autocomplete exige pelo menos 2 caracteres e devolve no máximo
       10 resultados.

     em ordem de implementação. Nenhum arquivo da aplicação será alterado por
     mim. Antes de escrever o .md, vou validar todo o código numa cópia do
     projeto no scratchpad: testes PHP, npm run build e checagem de tipos.

     laravel-vite-plugin. Ainda não há React. O vite.config.js usa a fonte

     App\Services\Clima\ClimaService,

     App\Models\Clima\ConsultaClima, App\Interfaces\WeatherProviderInterface
     etc.

     Decisões confirmadas com o usuário

     - React dentro do Laravel, em TypeScript, em resources/js, servido por uma
       view Blade na mesma origem (sem CORS).
     - Tabela do histórico: colunas Cidade, Consulta (data/hora), Temperatura,
       Sensação, Umidade e Descrição. Ficam fora: País, Observação e o chip de

     Decisões de design (minhas; ajustáveis na aprovação)

     - Vento e pressão: colunas nullable vento_kmh decimal(5,1) e pressao_hpa
       unsignedSmallInteger. A OpenWeather devolve wind.speed em m/s com
       units=metric; converto para km/h (×3,6), e a pressão vem de
       main.pressure. A regra de duplicidade continua comparando só os 4 campos 
       originais (temperatura, sensação, umidade e descrição). Quando o registro
       é redundante, atualizo o consultado_em e o vento e a pressão, para o
       card mostrar o valor mais recente. Registros antigos ficam com null, e o
       front exibe "—".
     - Histórico na API: GET 
       /api/clima/historico?cidade=&de=&ate=&page=&per_page=.
       - de e ate filtram o consultado_em, no formato Y-m-d H:i (valor do <input
         type="datetime-local">), com a regra ate >= de.
       - per_page é 1–50, com padrão 10. A resposta tem o formato padrão do
         paginator do Laravel (data, current_page, last_page, per_page, total,
         from, to).
       - Cache com versão: chave clima:historico:v{versao}:{md5(filtros)}, e
         cada gravação incrementa clima:historico:versao. Isso invalida todas as
         combinações de filtro de uma vez, já que o store database não suporta
         tags. O cache continua guardando arrays (->toArray() do paginator), por
         causa do serializable_classes => false.
     - Select de cidades do filtro: novo GET /api/clima/cidades, que lista os
       nomes distintos já consultados, com o mesmo cache versionado.
     - Dados do card: o front chama historico?cidade=X&per_page=50 (as 50
       consultas mais recentes da cidade, respeitando o período filtrado) e
       calcula a curva, a mínima, a média e a máxima no cliente. Com uma única
       consulta, mostra um aviso no lugar da curva.
     - Autocomplete: debounce de 300 ms e mínimo de 2 caracteres, chamando GET 
       /api/municipios. A sugestão mostra "Jales, SP", mas o POST envia só
       cidade=Jales, mantendo a decisão da parte 1.
     - Botões:
       - Consultar faz o POST /api/clima, recarrega o histórico e seleciona o
         registro retornado.
       - Cancelar aborta a requisição em andamento (AbortController).
       - Limpar zera o campo.
       - Recarregar busca o histórico de novo.
       - Filtrar e Limpar filtros aplicam e resetam os filtros.
     - Erros: um banner exibe a mensagem erro da API (404, 502 e 503) ou a
       primeira mensagem de validação (422).
     - Gráfico: SVG próprio, sem biblioteca, no estilo da tela (área com
       gradiente, ponto de pico e rótulos).
     - Tema: os tokens do DESIGN.md vão para o @theme do Tailwind v4 em
       resources/css/app.css. As fontes Inter, Plus Jakarta Sans e Material

● O problema está no routes/web.php: a rota foi escrita com Route::get em vez de
  Route::view. A migration em si está certa.

  Route::get('/', 'app');   // seu arquivo hoje
  Route::view('/', 'app');  // como está no .md

  O segundo argumento de Route::get precisa ser uma ação de controller (por
  exemplo 'Controller@metodo') ou uma função. A string 'app' não é nenhuma das
  duas, então o Laravel lança Invalid route action: [app] ao registrar a rota.

  O erro aparece até na migration porque o artisan carrega todos os arquivos de
  rotas ao iniciar. Por isso qualquer comando (migrate, test, serve…) falha
  enquanto essa linha estiver assim.

  Route::view('/', 'app') é o atalho do Laravel para "na URL /, mostre a view
  resources/views/app.blade.php", sem precisar de controller.

  O arquivo corrigido fica assim:

  <?php

  use Illuminate\Support\Facades\Route;

  Route::view('/', 'app');

  Testei numa cópia do seu projeto: com Route::get o erro se repete, e com
  Route::view o artisan volta a funcionar e lista as migrations normalmente. Não
  alterei o seu arquivo. Depois de corrigir, é só rodar php artisan migrate de
  novo.
